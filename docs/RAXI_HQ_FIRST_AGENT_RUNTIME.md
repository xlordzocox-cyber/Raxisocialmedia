Base: main `43b1ec3213c52b74ad0006c4499790533815bf40`. Rama independiente de staging: `feature/raxi-hq-director-research-runtime`. Este incremento contiene un núcleo ejecutable de servidor y pruebas locales, no un servicio alojado activo. No autoriza costes ni despliega un ejecutor. La quinta migración/campaign-command permanecen sin desplegar; este SQL no depende de ellos.

Correctivo P1: [política vigente, versión de autorización y despacho](../output/reports/raxi-hq-runtime/P1_POLICY_REVOCATION.md). Claim y despacho rechazan cambios REAL/simulación en ambos sentidos y cualquier cambio de configuración autorizada. El despacho es un punto de admisión; no hace atómicos PostgreSQL y el HTTP del proveedor ni cancela una llamada ya admitida/iniciada. Los recibos y costes posteriores a una revocación se conservan.

Segundo correctivo P1: [procedencia de expiración y contrato completo de 192 KiB](../output/reports/raxi-hq-runtime/P1_EXPIRY_RESULT_SIZE.md). La expiración conserva el modo del run vencido, su identidad y auditoría. SIMULATED nunca produce evidencia verificada ni agentes reales en Pixi. El resultado completo cuenta bytes UTF-8 con escapes/metadatos; las fuentes verificadas se conservan completas, citadas o no. Los límites de campo y de SQL son compatibles.

## Recorrido acotado

1. `requestHandler` recibe JWT y comando humano `{workspaceId, requestKey, spec}`. El host debe proporcionar verificación Auth real con `getUser(token)`; no se acepta actor del cuerpo. Se limita tamaño y campos. Una autorización captura pregunta, investigación externa sí/no, proveedor/modelo, límite de coste y caducidad. `raxi_runtime_request` verifica propietario y política habilitada de servidor, reserva presupuesto y persiste tarea, aprobación TASK y auditoría en una transacción. El modelo no dispone de ese endpoint como herramienta.
2. Un proceso servidor autorizado toma el ID de esa tarea y llama `runOne`. `raxi_runtime_claim` reclama Director o Investigador según el prefijo ya confirmado; mantiene un intento por paso y lease de 90 segundos. Los locks son cortos y nunca abarcan la llamada a IA. Índices parciales impiden dos intentos activos de una tarea o agente. Una petición duplicada con el mismo contenido conserva la tarea; contenido distinto bajo la misma clave es conflicto.
3. El adaptador llama al proveedor fuera de la transacción con timeout de 45 segundos. Solo un recibo auténtico permite ACK y eventos operativos. El resultado se valida antes de confirmar: estructura cerrada, tamaño, citas y fuentes permitidas. Director entrega un brief textual limitado, no permisos ni herramientas al Investigador. En este primer adaptador no hay streaming: Responses se confirma después de completar su respuesta, por lo que RUNNING puede durar muy poco. No se fabrica progreso previo a esa confirmación.
4. Cada paso conserva run, intento, trabajador, proveedor/modelo, reserva, coste si se conoce, recibo, resultado y eventos/auditoría. Tras Director confirmado, otro proceso puede continuar con Investigador sin repetir el primero. Un resultado incierto conserva la reserva, queda UNKNOWN/BLOCKED y exige reconciliación humana antes de autorizar un trabajo nuevo. No hay reintento automático de un efecto pagado ni promesa de exactly-once en la API de IA.
5. `raxi_runtime_office` recupera una proyección autenticada por propietario, sin lease tokens ni credenciales de worker. `RuntimeOfficeStore` la convierte a HQState para la misma OfficeScene/Pixi; no fabrica tareas ni eventos. Excluye simulaciones, rechaza duplicados/ámbitos ajenos y caduca RUNNING por lease incluso si falla la red. El panel tiene su propia lectura/estado, independiente del HQStore/Munder existente. El botón de solicitud permanece deshabilitado hasta habilitar explícitamente el servicio y revisar la experiencia de autorización. El recorrido de solicitud es actualmente API de servidor probada, no un formulario de producción habilitado.

## Cambios de base propuestos

`supabase/proposals/agent_runtime.sql` está deliberadamente fuera de `migrations/`. No se ha aplicado remotamente ni representa una sexta migración autorizada. Reutiliza perfiles, tareas, eventos, aprobaciones y auditoría existentes; añade políticas de presupuesto y `raxi_agent_runs`, y amplía el tipo de sujeto de aprobación con TASK. Las tablas nuevas tienen RLS y revocaciones; solo el servidor puede escribir o leer tokens de lease. Las RPC de escritura son invoker exclusivas de `service_role`, con comprobaciones explícitas de propietario, transición y autorización. Los propietarios solo consultan la proyección segura.

Una revisión futura deberá convertir esta propuesta en una migración generada con la CLI, comprobar inventario/advisors, compatibilidad y ensayar contención física antes de autorizarla. El SQL se aplica únicamente a bases nuevas PGlite en las pruebas. No cambiar políticas/filas de producción para probarlo.

## Adaptadores, secretos y fuentes

- `simulatedProvider`: resultados y recibos SIMULATED, eventos MOCK/UNVERIFIED, coste conocido cero. No aparecen como agentes IA reales en Pixi. Las pruebas simuladas nunca acreditan una ejecución de IA auténtica.
- `openAIProvider`: adaptador de servidor de Responses con clave inyectada por el host; tanto el adaptador como el coordinador requieren habilitación explícita. Sin modelo predeterminado ni clave buscada en el navegador. Usa `store:false`, límite de salida y ninguna herramienta. Está preparado según [OpenAI Docs](https://developers.openai.com/api/docs/guides/text), pero no se ha llamado a OpenAI ni se ha elegido un modelo/coste para ejecución.
- Otros proveedores pueden registrarse mediante `Provider`, sin ampliar permisos. La política de servidor debe coincidir en proveedor/modelo y distinguir simulación. No se añade un API genérico que acepte URLs de proveedor desde el usuario.
- Investigación externa exige un recuperador de fuentes de servidor aún no conectado, con allowlist de hosts, contenido limitado, fecha y SHA-256 comprobado. Las citas solo pueden referir IDs de ese material. Si falta el recuperador o falla integridad/citación, no hay resultado aceptado. Contenido externo y salida previa se envían como datos no fiables; no se ejecutan herramientas, comandos, aprobaciones o instrucciones que contengan. Esto limita efectos de prompt injection, sin afirmar que un resumen de modelo sea infalible.
- Tener citas verificables no equivale a fact-check humano: el resultado conserva `CITED_SOURCES_NOT_FACT_CHECKED` o `MODEL_OUTPUT_NOT_FACT_CHECKED`. La evidencia VERIFIED de un evento confirma el recibo operativo, no la verdad de una afirmación del modelo.

Supabase conserva el registro operativo; Supermemory puede aportar contexto complementario permitido sin credenciales y sin sustituir tareas, recibos, auditoría o backups. No se conecta memoria privada automáticamente. Munder y Aria son integraciones separadas y ninguna es requisito del recorrido de investigación textual.

## Límites de uso y costes

Política por workspace deshabilitada por defecto: proveedor/modelo, presupuesto total acumulado, reserva por llamada, máximo de tareas, tokens de salida y vencimiento. Dos llamadas como máximo por tarea, un intento por paso. La reserva se conserva incluso con coste desconocido o resultado incierto. No se inventa coste monetario a partir de tokens: Responses devuelve uso, que no es una factura; `cost_micros` queda null salvo recibo de coste conocido.

La reserva limita el plan autorizado; **no sustituye un límite de facturación del proveedor**. Antes de habilitar real deben revisarse precios vigentes, cota de entrada/salida, presupuesto del proyecto proveedor y mecanismo de parada. Una política o un resultado del Director no autorizan exceder el importe humano. Si no se puede establecer una cota aceptable, mantener live deshabilitado. No hay habilitación de Aria, imágenes, redes o compras.

El coordinador comprueba que queda lease y autorización suficientes para la llamada acotada después de recuperar fuentes, antes de contactar IA. Si un recibo de coste conocido supera la reserva, la operación queda bloqueada y la política se deshabilita conservando ese coste; no se oculta como cero ni se aprueba el exceso.

## Conexiones faltantes y primera prueba real propuesta

Faltan un Supabase de ensayo autorizado, aplicación revisada de esta propuesta solo allí, host servidor/cola autenticada que monte `requestHandler` y ejecute tareas aprobadas, secretos de ese host, cuenta/proyecto API con modelo disponible y facturación/límites, y autorización humana con una cotización concreta. La UI consulta y muestra indisponibilidad; no está desplegado un endpoint de solicitud ni un worker. No se configura autoejecución al importar módulos o iniciar HQ.

Primera prueba a autorizar después: una pregunta textual aportada por Luis, sin investigación externa, dos llamadas Director/Investigador, máximo 256 tokens de salida por llamada, entrada acotada y un solo trabajo. Mostrar antes proveedor, modelo exacto, precio vigente, cota monetaria total y caducidad; no arrancar hasta aprobarlos. Aceptar solo si existen Auth real, aprobación persistida, dos recibos reales, resultado, auditoría y proyección de oficina confirmados. Después reconciliar coste conocido/pendiente y revocar la política. El ensayo requiere coste de proyecto/compute/almacenamiento/egress de Supabase, host del worker y dos llamadas de texto; investigación externa añadiría un servicio de recuperación y su coste. Importes y servicios concretos quedan pendientes de selección/autorización, sin crear nada para cotizar.
